What Makes This Uniquely Hard
🔀
FIFO Payment Allocation — The Hardest Problem
When a customer pays a lump sum covering future events, that money must be allocated to each event in the exact order it occurs. Bond runs three parallel FIFO allocators:
Reservation FIFO
Slots & ice time. A documented platform bug silently changes reservation IDs mid-lifecycle — recovered via FIRST_VALUE window function. Addon payments spread proportionally by price weight.
Registration FIFO
Events & classes. 5-level canonical ordering (events before payments, discounts before reversals). LAST_VALUE IGNORE NULLS forward-fills price-per-event. Orphaned payments surfaced as identifiable rows — never dropped.
Punch Pass FIFO
Prepaid bundles for N events. Revenue recognized per event attended, not per pass sold. A synthetic remainder row (event_id = -1) absorbs unrecognized balance when fewer events are attended than purchased.
📒
Accrual Across 7 Product Streams
Events, slots, leagues, memberships, registrations, goods, and convenience fees all unioned into a single ledger — each with its own recognition method (evenly/daily, on event occurrence, milestone). The daily-spread method requires generating up to 2,000 synthetic date rows per line item using Snowflake's LATERAL GENERATOR. A built-in constraint enforces Assets = Liabilities + Equity at every row — failure means the dbt run fails before reaching production.
🔧
Building on a Live, Moving Platform
The Bond platform is actively developed. Analytics absorbs its instability without exposing it downstream. Real production workarounds: slots silently changing reservation IDs (FIRST_VALUE recovery), migration data where the first action is a payment (LEFT JOIN exclusion — NOT IN caused query timeouts at scale), and synthetic line_item_ids for convenience fees that require LEFT JOINs on every downstream join.
⚖️
GAAP Accrual Without an Accounting System
Most analytics stacks read clean transactional data and aggregate it. This stack computes double-entry accounting balances — AR, Deferred Revenue, Recognized Revenue — entirely in dbt SQL, without a general ledger system. Every number a finance team sees is derived, tested, and reconciliation-checked before it leaves Snowflake.
