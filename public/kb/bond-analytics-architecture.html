What Bond Analytics is
The single source of truth for all Bond financial and operational data

Bond Analytics is the data infrastructure layer that sits between the Bond platform and every downstream decision. Raw operational data flows in from the Bond platform, Stripe, Salesforce, and other systems — and comes out the other side as structured, tested, reliable models that power board reports, customer health dashboards, finance exports, and internal tools.

Every number in a Sigma report, every row in a finance export, and every metric in a board deck traces back to a model in this stack.

Flagship
Actions Ledger
The financial backbone of Bond Analytics

A full double-entry accrual ledger that tracks every dollar of revenue across the entire Bond platform — from the moment a customer is invoiced, through payment, through recognition. Every financial statement traces back here.

The Actions Ledger unifies 7 product streams (events, slots, registrations, leagues, memberships, goods, convenience fees) into a single coherent view with canonical accounting balances: Accounts Receivable, Deferred Revenue, and Recognized Revenue. A built-in sanity check enforces that Assets = Liabilities + Equity at every row — if it doesn't balance, the model fails before it reaches production.

What makes this uniquely hard
Problems most analytics teams never face

Most analytics stacks read clean transactional data and aggregate it. Bond Analytics can't do that — the underlying financial reality is too complex. These are the problems that don't exist in a standard analytics role and that make the work here genuinely uncommon.

Hardest problem
FIFO Payment Allocation

When a customer pays a lump sum that covers future events, that money can't just sit as a payment — it has to be allocated to each event in the exact order it occurs. Sounds simple. It isn't.

Bond runs three parallel FIFO allocators, each with different logic:

Reservation FIFO
Matches payments to ice time and slot reservations in canonical order. Addon payments (e.g. equipment) are spread proportionally across slots by price weight. A documented platform bug allows slots to silently change their reservation ID mid-lifecycle — the allocator detects this using a window function and recovers the original ID rather than misallocating revenue.
Registration FIFO
Matches payments to event and class registrations. Uses a 5-level canonical ordering — events before payments, discounts before discount reversals — and forward-fills price-per-event onto payment rows using LAST_VALUE IGNORE NULLS. Orphaned payments (where no matching event exists) are captured with a synthetic action key suffix rather than dropped silently.
Punch Pass FIFO
Punch passes are prepaid bundles for N events. Revenue can only be recognized per event attended, not per pass sold. If a customer attends fewer events than their pass allows, a synthetic remainder row (event_id = -1) absorbs the unrecognized balance. This prevents over-recognition while still keeping the books balanced.
Every allocator includes an explicit orphaned-payment handler — no dollar is silently dropped. If a payment can't be matched, it's surfaced as an identifiable row rather than disappearing into the void.
Revenue Recognition Across 7 Product Streams

Most platforms recognize revenue when payment clears. Bond recognizes revenue when it's earned — which is different for every product type on the platform.

The accrual engine unifies 7 product streams (events, slots, leagues, memberships, registrations, goods, convenience fees) into a single ledger, applying one of three recognition methods per line item:

Evenly from start
Revenue spread daily across the service period. Requires generating up to 2,000 synthetic date rows per line item using Snowflake's LATERAL GENERATOR — there's no other way to do it in pure SQL.
On event occurrence
Recognition triggered when a specific event happens (e.g. a class runs, a slot is consumed). This is the core of the FIFO allocator problem — the event has to actually occur before the money is real.
Milestone-based
Revenue recognized at defined checkpoints regardless of daily spread. Used for goods and certain league fee structures.
A built-in sanity check enforces Assets = Liabilities + Equity at every row. If the ledger goes out of balance, the dbt run fails before anything reaches production.
Building on a Moving Platform

The Bond platform is a live, actively developed product. The data layer underneath it is not stable — and Analytics has to absorb that instability without exposing it downstream.

Real examples from production code:

Slot reservation_id drift
Slots can silently change their reservation_id in the platform database mid-lifecycle. A FIRST_VALUE window function recovers the original ID so the allocator doesn't misroute payments.
Migration data anomalies
Historical data migrated from legacy systems includes line items where the first recorded action is a payment — which is impossible in the normal flow. These rows are excluded via a LEFT JOIN anti-pattern; a NOT IN clause caused query timeouts at scale.
Synthetic IDs for convenience fees
Convenience fees don't have real line_item_ids in the platform — they're generated synthetically in dbt. Every downstream join has to use a LEFT JOIN to avoid dropping them.
Each of these represents a permanent dbt workaround for a platform behavior that can't be changed without a full data migration. The stack absorbs the complexity so nothing surfaces to customers or finance.
Key design decisions
Why it's built this way

Every meaningful architectural choice has a reason. These are the five decisions that define how Bond Analytics works — explained in terms of what they protect against, not just what they are.

1
Double-entry accrual ledger — not cash-based accounting
The actions model: Revenue recognized when earned, not when paid
Why it matters

Cash accounting is simple but wrong for a platform business. A customer can pay for 10 events in January and run them through June — cash accounting books the revenue in January; accrual accounting spreads it correctly. Bond's board reports and financial statements need GAAP-compliant recognition. A cash-based model would materially misstate revenue in any period where pre-payment and delivery don't align.

How it's implemented

The Actions Ledger uses a full double-entry model: every financial event creates a debit and a credit across AR, Deferred Revenue, and Recognized Revenue accounts. Running balances are computed via window functions. A built-in constraint — Assets = Liabilities + Equity — is enforced at every row. If the model goes out of balance, it fails the dbt run before reaching production.

2
FIFO payment allocators for every revenue stream
Matching payments to revenue events in strict chronological order
Why it matters

When a customer makes a lump-sum payment that covers multiple future events, that payment must be allocated correctly to each event as it occurs — otherwise revenue is either over-recognized (booked too early) or under-recognized (missed). Without a FIFO allocator, partial payments, refunds, and multi-event invoices produce incorrect ledger balances that are nearly impossible to audit.

How it's implemented

Two parallel FIFO processors — one for reservations (slots/ice time) and one for registrations (events/classes) — each with their own canonical ordering logic and running payment balance computation. A third path handles punch passes, which have a unique "remainder" accounting treatment. Each processor has explicit orphaned payment handling so no dollar is silently dropped.

3
dbt over raw SQL — version control, testing, and documentation as requirements
Every transformation is a reproducible, tested, documented artifact
Why it matters

Raw SQL in a warehouse is a black box. It can't be version-controlled cleanly, it doesn't self-document, and there's no standard way to test it. When a number in a board report is wrong, finding the root cause in raw SQL means manually tracing through warehouse query history. With dbt, every model has a git history, a lineage graph, and a test suite — bugs are findable in minutes, not hours.

How it's implemented

All 287 models are dbt SQL files with .yml documentation and dbt tests (not_null, unique, relationship checks). SQL style is enforced via sqlfluff. Models run on dbt Cloud on a production schedule. The lineage graph is auto-generated — anyone can see exactly which models feed which outputs without asking the team.

4
Snowflake as the single source of truth
All data in, all data out — no system talks directly to another
Why it matters

When data flows directly between systems (e.g., Stripe → Salesforce, or Bond platform → Sigma), every integration is a custom pipe that breaks independently and has no shared audit trail. Two systems can disagree on a number and there's no referee. Routing everything through Snowflake means there is always one authoritative version of every number — and one place to look when they don't match.

How it's implemented

All source systems land in RAW (Bond platform, Stripe, Payout Service, Open Exchange Rates). All transformed outputs live in ANALYTICS. All downstream consumers (Sigma, Qlik, finance exports, data share) pull from ANALYTICS. Live external data (Salesforce, Stripe Share) is accessed via Snowflake's data sharing, keeping the warehouse as the query layer without requiring a copy.

5
Read-only access pattern for analysts and AI tools
Two-layer lockdown: Snowflake RBAC + MCP config blocking all writes
Why it matters

The production data warehouse is not a development environment. Giving analysts or AI tools write access creates real risk of accidental data modification — especially as Claude and other AI agents become capable of running SQL autonomously. A SELECT-only role makes it safe to give broad access without worrying about what someone (or something) might accidentally change.

How it's implemented

Two enforcement layers: (1) A BOND_READONLY Snowflake role with SELECT-only grants on ANALYTICS — no INSERT, UPDATE, DELETE, or DDL. (2) An MCP config file that explicitly blocks all write SQL statement types at the tool level, regardless of what the Snowflake role technically permits. Both layers must be bypassed to accidentally modify data — that's intentional.
